# ADR 0006 — Telemetry schema for Laravel 13 events

**Status:** accepted (Milestone 1)
**Implements:** handoff §6.2/§6.3, adjusted to the verified 13.x payloads.

## Context

Handoff §6.2 lists `JobProcessing`, `JobProcessed`, `JobExceptionOccurred`, `JobFailed`
and "`JobReleasedAfterException`, if available", and asks for status from the event
name. Laravel 13 makes that insufficient:

- `JobProcessed` also fires when the job was deleted for exceeding attempts, and a job
  can be released or failed during `handle()`.
- `JobAttempted` changed payload in 13: `$exception` (object|null) replaced the boolean
  `$exceptionOccurred`; code copied from a 12.x example silently reports `true`/`false`
  in the wrong field.
- Retry semantics are richer than "failed": `JobReleasedAfterException` carries the
  backoff, and `JobTimedOut` is a distinct outcome.
- A failed job's exception message may contain credentials (DSNs, Redis URLs, tokens).

## Decision

1. The package emits a **terminal event per attempt**, not one event per framework
   event. `JobProcessing` opens an attempt keyed by job UUID (fallback: job id);
   the next terminal event closes it with `outcome ∈ {processed, released, failed,
   timed_out}`. Several Laravel events may collapse into one
   terminal record; the record carries `attempt` and `duration_ms`. The vocabulary is
   one contract for both halves of the product: `tests/fixtures/telemetry-outcomes.json`
   is read by the Go and PHP test suites, so neither can add an outcome alone. Real workers
   now produce all four: `ReleaseOnce` releases its first attempt and fails the retry, and
   `Hang` is reported as `timed_out` before the worker is killed for it.
2. Status is derived from job flags (`hasFailed()`, `isReleased()`), not from the event
   class. `JobProcessed` alone is never "success". `isDeleted()` is deliberately not
   consulted: Laravel deletes every job as part of finishing it, so the flag is true on
   each successful run and distinguishes nothing.
3. Event shape (Redis Stream field `payload`, JSON):

   ```json
   {
     "schema": 1,
     "id": "uuid-v4",
     "type": "job.finished",
     "application": "production",
     "environment": "production",
     "worker": "gohorizon:production:production:default-supervisor:1a2b3c4d",
     "at": "2026-11-20T10:11:12.345Z",
     "job": {
       "uuid": "…", "id": "…", "class": "App\\Jobs\\SendMail",
       "connection": "redis", "queue": "emails", "attempts": 2,
       "outcome": "released", "duration_ms": 1841,
       "exception": {"class": "RuntimeException", "message": "…"}
     },
     "tags": ["mail"]
   }
   ```
4. Never emitted: the raw payload, serialized job arguments, command output, headers,
   stack traces, or the exception message before sanitization. Sanitization redacts
   `scheme://user:pass@host`, `password=`/`token=`/`secret=` values, and bearer tokens,
   then truncates to 512 characters.
5. The event `id` is a UUID generated by the publisher; the Go consumer uses it for
   deduplication (handoff §14.6 idempotency) and records it in the stream entry. Stream
   entries also get `XADD MAXLEN ~ retention` from configuration.
6. Emission is best-effort and bounded: a in-process buffer (`telemetry.batch_size`,
   `telemetry.buffer_size`) flushed on batch full, on `WorkerStopping`, and on
   `register_shutdown_function`. Publish failures are counted and dropped after the
   buffer overflows; they never throw into the job path (handoff §2.11, §6.3).

## Consequences

- One event per attempt means throughput numbers do not double-count retries.
- The schema is versioned (`schema: 1`); Go rejects unknown schemas instead of guessing.
- The outcome set is closed at four values. An event carrying anything else is rejected
  and counted as invalid, so a typo in the publisher cannot quietly invent a new column.
- Losing the buffer on SIGKILL is accepted: telemetry is observation, never a job ledger.
